# 世界数据与移动移植状态

运行时为 C++17，不加载 JVM。`world.cpp` 的依据是所给 MCP 1.8.9 源码中的 `Entity`、`EntityLivingBase`、`EntityPlayer`、`EntityPlayerSP`、`AxisAlignedBB`、`World` 和各方块类。

## 已移植与验证

`Player::tick(world, input)` 执行一个 50 ms 游戏刻；调用方使用固定 20 Hz 时钟，渲染帧率不参与物理计算。位置表示脚底，yaw 0 朝 +Z，yaw 90 朝 -X。正向 strafe 对应原版左键。

- 地面、空中加速，斜向输入归一化，惯性、摩擦、重力、跳跃冷却。
- 跑步键、双击前进、饥饿限制、潜行与使用物品减速。
- 按 Y/X/Z 顺序的 AABB 碰撞，两条候选路径的自动跨台阶，以及潜行边缘保护。
- 冰、黏液块、灵魂沙、蜘蛛网、梯子、藤蔓、跳跃提升，飞行与飞行切换。
- 水和岩浆阻力、浮力、流水推动、深海探索者系数；进入水面时再次执行原版落地状态中的水检测。
- 1.8.9 静态方块碰撞形状，包括上下半砖、内外角楼梯、门、活板门、连接栅栏/围墙/玻璃板、箱子、雪层、蛋糕、可可果、铁砧、漏斗、炼药锅及静止的活塞底座/头。
- 世界边界的虚拟石头碰撞、±1 格内外状态迟滞，包括建筑高度以上的边界；网络层按真实时间插值边界直径。
- 当前区块尚未加载时跳过移动，与 `EntityPlayerSP.onUpdate` 一致。

注意原版的农田碰撞高 1 格，单层雪碰撞高 0 格；视觉模型的尺寸不能代替碰撞尺寸。方块形状读取相邻方块的元数据。

## Java 差分验证

从项目目录执行：

```powershell
python tools/verify_physics.py --mcp ../MCP-919-main
```

测试需要开发机的 JDK 17、Python 和 C++ 编译器。它重新编译所给源码中的物理、世界、边界和全部方块类；MCP 的 `bin/minecraft` 和原版 jar 仅提供其余依赖及语言资源。`EntityPlayerSP` 的输入与跑步/飞行前置代码从源文件逐段提取。测试世界没有图形、网络、音频或活跃实体。

当前结果为 **69,115 行全部精确相等**：65,543 个 sin/cos 样本、1,516 个碰撞形状样本、2,056 个逐刻移动状态。比较位置、速度、落地/碰撞状态、跑步、潜行、飞行、下落距离、水/岩浆/蜘蛛网和边界状态，按输出的 17 位有效数字还原 double 后要求完全相等。报告和源文件 SHA-256 在 `build/physics_reference/report.json`，两侧轨迹也保存在该目录。

测试包括行走与停止、任意朝向的斜走、跑跳、连续跳跃、跳跃提升、物品减速、饥饿限制、服务器移动属性、冰、黏液、灵魂沙、台阶、顶头碰撞、梯子、蜘蛛网、水面进出、流水、岩浆、飞行、边界阻挡和区块未加载。

形状测试显式调用原版 `setBlockBoundsBasedOnState`。1.8 的 `Block` 使用共享、可变的包围盒字段，例如铁砧可能保留上次渲染/射线查询写入的尺寸。C++ 使用当前方块状态的确定形状，并未复制整个 Java 渲染时序造成的这类全局缓存副作用。

普通 C++ 测试为 `tests/world_tests.cpp`，同时检查区块解码、负坐标、截断数据不修改世界、光照 nibble 顺序、完整/部分更新、批量载入、卸载、边界网格失效及基本物理。

## 浮点规则

物理模块禁止 `-ffast-math`、`-Ofast` 和隐式融合乘加。GCC 使用 `-ffp-contract=off -fno-fast-math`；MSVC 使用 `/fp:strict`。不要将全部常量改成 double：原版在 float 中完成输入、三角查表、加速和摩擦系数运算，然后转换为 double 积分。人物宽度为 `double(0.6f)`、高度为 `double(1.8f)`、跳跃速度为 `double(0.42f)`。sin/cos 使用原版 65,536 项查表和截断索引。

`movementSpeed` 是已应用服务器修饰符、但尚未包含本地跑步修饰符的移动属性。跑步加成为原版 operation 2 的 `0.30000001192092896`。`flightChangesLastTick` 保存同一刻内有序的飞行切换，网络层逐一发送 C13，包括先开启再因落地关闭的情况。位置校正调用 `teleport`；该方法保留速度，由协议层按 S08 标志处理相对坐标和速度清零。

## 世界存储与光照

按需分配 16×16×16 节，共 16 节组成 16×256×16 区块。每格 `uint16_t` 保存 `block_id << 4 | metadata`；节内索引为 `(y << 8) | (z << 4) | x`。保留原始方块光、天空光、256 字节群系数组。

S21 与 S26 的状态数组按小端读取，其他协议头由网络模块处理。所有长度和坐标在写入前验证。完整更新丢弃未列出的节，部分更新保留未列出的节。S21 的完整零掩码是卸载，而 S26 的零掩码是已加载的空气区块。未知状态原样保存，不假装支持其行为。

S21 按原版 `Chunk.fillChunk` 只要求消费所需的最少字节，并忽略受协议帧大小限制的尾部数据；S26 仍要求精确长度。已用实际收到的末地区块包验证：服务器在末地附带了天空光数组，原版仍按“无天空光”读取，因而把第一段天空光当成群系并忽略剩余字节。实现保持此原版偏移，不根据多余数据猜测维度。`tools/verify_chunk_capture.py` 对实际 49,422 字节 S21 消息重新运行原始 Java `Chunk.fillChunk`，消费后的 41,216 字节状态/光照/群系与 C++ 完全一致；报告为 `build/chunk_reference/report.json`。

世界和区块版本号供渲染缓存失效；更新也标记八个相邻区块，覆盖面剔除、连接模型和 AO 的依赖。`clear()` 清除区块而保留世界边界；新构造的世界及 `generatePreview()` 使用原版默认边界。

离线预览生成器是固定种子的演示地形，**不是原版世界生成器**。它单独计算直射天空光，并通过邻格传播照亮树冠下方、斜坡和悬空物体下方。网络接收的光照不会被这个预览过程覆盖。运行时完整光照重算、红石和方块随机刻仍需独立实现；原版分阶段世界生成见 [WORLDGEN.md](WORLDGEN.md)。

`World::waterAcceleration(query)` 为掉落物、经验球等调用方提供原版水流查询，直接使用传入的 AABB，不附加玩家的收缩范围。结果包含 `loaded`、`inside`、`hasFlow`，以及已经归一化并乘以 `0.014` 的增量；只有 `hasFlow` 且实体允许被水推动时才相加。长度按 `Vec3.normalize` 先将平方根转换为 float，再提升为 double。此公共接口加入后，69,115 行玩家物理对照保持通过；下游掉落物／经验球测试另有水流、下落水与碰撞覆盖。

## 尚不能宣称完全一致的部分

这些测试证明列出的确定场景与原源码一致，不能证明全部游戏状态或任何反作弊插件都接受该客户端。

- 尚未实现实体碰撞/推动、船、矿车、坐骑、移动活塞方块实体、睡眠、完整死亡和重生生命周期。
- 物品、附魔、药水、属性、饥饿和实体元数据需要调用方提供完整状态；当前客户端的全部游戏系统尚未齐全。
- 静态形状测试没有穷举所有邻居组合、所有游戏事件顺序、所有极端坐标和原版共享可变包围盒的副作用。
- 光照字节保留与地形持久化不等于完整的世界模拟。原版区块的方块实体、实体、红石和计划刻需要独立处理。
- `warnings` 显式报告缺区块、实体交互未实现、附近移动活塞、未知方块和流体环境。流体环境仍保守标记，尽管所列流水/浮力轨迹已通过差分测试。

异常的非有限位置、超过 512 格/刻的位移及超大碰撞查询被拒绝；这些输入不属于验证范围。
